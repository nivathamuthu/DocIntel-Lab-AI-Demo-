How it works

One model call writes the function. A separate call writes test cases from the rule text: condition, action and exception. The tests come from the rule text, not from the code, so the code cannot cheat. If tests fail, the model sees the pytest output and repairs the code; the tests never change.

Passing tests show the code agrees with the model's own reading of the rule, not that the rule or that reading is correct. When a test fails, a separate call judges it against the rule text: a wrong test is dropped and the code kept, an ambiguous rule stops the run for review, and a repair may not change a number from the rule text. A person still reviews the result.

Demo sandbox, not a security boundary

Tests run with pytest in a separate python -I process, in a temporary folder, with no secrets in its environment, sockets disabled and a {{ timeout }}-second timeout. Imports such as os, subprocess, socket, requests and shutil are refused before anything runs. Determined code could still get around this, so do not run untrusted rules outside a demo.
